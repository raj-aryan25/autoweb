# Running password and email verification login

Run commands from this repository in conda `autoweb`. On this machine the root is
`/home/raj/Codec/autoweb`; use your actual checkout path on Windows.

## Practice site: password login first

`configs/sites/practice-test-login.json` targets the public demonstration at
<https://practicetestautomation.com/practice-test-login/>. Its published demo
credentials belong in the ignored root `.env`:

```dotenv
PRACTICE_LOGIN_USERNAME=student
PRACTICE_LOGIN_PASSWORD=Password123
```

These entries have been added locally without replacing other `.env` settings.
The profile checks the success heading, Log out link, and destination URL. This
site demonstrates password login; it does not provide an email OTP challenge.
The live CLI smoke test passed using the published account. The rejection check
uses the site's `#error.show` state; submission has a 30-second redirect budget.

```sh
conda run -n autoweb python -m autoweb.login --site configs/sites/practice-test-login.json
```

Add `--headed` on a machine with a graphical display. The CLI closes the browser
after confirming success. Use `authenticated_session` in Python to keep the page
open for further work. No Gmail or OAuth configuration is needed for this profile.

To watch the actions at a slower pace for one run:

```sh
conda run --no-capture-output -n autoweb python -m autoweb.login --site configs/sites/practice-test-login.json --headed --slowmo
```

`--slowmo` uses 700 ms; `--slowmo 1200` selects a custom delay. It works in
headless mode too. Without the flag the configured delay applies (normally 0).
If you previously added `AUTOWEB_SLOW_MO_MS` to `.env`, remove that entry once
to use only the flag, or pass `--slowmo 0` to override it for a run.

## Where to change settings

| File | What goes there |
| --- | --- |
| `.env` at the repository root | Account values and environment overrides; ignored by Git |
| `.env.example` | Documented variable names; no private account values |
| `configs/sites/<your-site>.local.json` | Login URL, steps, selectors, email filters, success/failure checks; ignored by Git |
| `configs/settings.json` | Shared browser, timeout, Gmail path, and AI defaults |
| `configs/settings.local.json` | Optional local defaults, selected with `--settings`; ignored by Git |
| `secrets/gmail/credentials.json` | Google desktop OAuth client file, when setting up Gmail later |
| `secrets/gmail/token.json` | OAuth token generated by explicit authorization later |

Existing `.env` values are preserved. Process environment variables override `.env`.
All relative paths resolve against the repository root. To use another root or
dotenv file, pass `--project-root` or `--env-file`. See
[all environment overrides](../configs/README.md).

## Email login after OAuth setup is requested

Copy `configs/sites/email-otp.example.json` or
`configs/sites/password-email-otp.example.json` to a `*.local.json` file. These
are templates using example.com, not working external-site profiles. Update:

- `entry_url`, identifier/password controls, and required button selectors.
- `request_otp`: the single click that actually sends the email. For password
  plus OTP this can be the password form's submit button.
- `fill_otp.targets`: one code field, or one locator per character for split inputs.
- `verification.sender` and `subject`: the site's actual verification email filters.
- `verification.recipient.env`: the `.env` variable holding the receiving account.
- `verification.rejected` and `expired`: visible error assertions for those states.
- `success`: real authenticated UI, and optionally an API/session assertion.
- `failure`: credential rejection checks; avoid matching a normal signed-out page.

For the example references, set `EXAMPLE_EMAIL`, and for password plus email OTP
also `EXAMPLE_USERNAME` and `EXAMPLE_PASSWORD`, in `.env`. Rename the references
in a local profile if you prefer site-specific variable names. AI is optional
and disabled by default; `GOOGLE_API_KEY` is not needed for deterministic extraction.

Only when ready to configure OAuth, install Gmail support and authorize the mailbox:

```sh
conda run -n autoweb python -m pip install -e '.[gmail,test]'
conda run -n autoweb python -m playwright install chromium
conda run -n autoweb python -m autoweb.gmail --authorize
conda run -n autoweb python -m autoweb.config --site configs/sites/your-site.local.json
conda run -n autoweb python -m autoweb.login --site configs/sites/your-site.local.json
```

OAuth is a separate explicit operation; the login runner loads an existing token
before opening the website. To reuse existing OAuth files, set
`AUTOWEB_GMAIL_CREDENTIALS_FILE` and `AUTOWEB_GMAIL_TOKEN_FILE` in `.env` to their
absolute paths. They are not moved or overwritten as part of Phase V setup.
See [Gmail setup](../src/autoweb/gmail/README.md) for consent and scopes.

## Challenge behavior and deterministic checks

The runner captures baseline message IDs before requesting the code and records
the challenge timestamp immediately before the request click. One deadline covers
baseline, request, polling, code entry, submission, authentication, and acknowledgment,
capped by the total login budget. Polling can use more time than a browser action.

The browser context stays the same throughout. Codes keep leading zeros. Stale,
baseline, or mismatched provider results never reach an input. Incorrect/expired
codes produce `verification_rejected`/`verification_expired`; no mail produces
`verification_timeout`. Missing transitions fail within configured action/challenge
budgets. Request, submit, and resend actions are never automatically repeated;
automatic resend count is zero. Start a new attempt explicitly after inspecting
the site's state; each attempt captures a new baseline and timestamp.

Mail is marked read only after all authentication checks pass, according to
`verification.acknowledge` (`on_success` or `never`). An acknowledgment API failure
is reported at the `acknowledgment` stage even though website authentication was
already confirmed; do not automatically resubmit a login in response. OTP fields
are masked in failure screenshots.

```sh
conda run -n autoweb python -m pytest tests/integration/test_email_login.py -q
conda run -n autoweb python -m pytest -q
```

The deterministic tests use local Chromium, a fake provider, and the real Gmail
poller over a synthetic mailbox. No live Gmail or Gemini calls are made. Live
email verification remains opt-in and needs a site that actually sends an OTP.
