# Manual verification of Phases I-IV

Use PowerShell. Run all commands from `D:/RAJ ARYAN/Codec/AutoWeb` in conda
`autoweb`. Password browser login and Gmail retrieval are independently runnable.
The browser does not yet request or submit email codes; that is Phase V.

## 1. Prepare the environment

```powershell
Set-Location "D:/RAJ ARYAN/Codec/AutoWeb"
git switch dev
conda run -n autoweb python -m pip install -e ".[gmail,test]"
conda run -n autoweb python -m playwright install chromium
conda run -n autoweb python -m pip check
```

Keep development/configuration changes on `dev`. Installing Chromium is only
needed if the matching binary is missing. Expect `No broken requirements found`.
If conda is unavailable in PowerShell, open a conda-enabled prompt.

## 2. Run deterministic checks without real credentials

```powershell
conda run -n autoweb python -m pytest -q
conda run -n autoweb python -m autoweb.config --site configs/sites/local-password.example.json --env-file configs/demo.env.example
```

The current full suite has 226 tests. It uses local Chromium sites and fake Gmail,
OAuth, and Gemini boundaries. Expect all tests to pass and the configuration
command to print `Valid configuration and credential references`.

For focused checks:

```powershell
conda run -n autoweb python -m pytest tests/integration/test_browser.py -q
conda run -n autoweb python -m pytest tests/integration/test_login.py -q
conda run -n autoweb python -m pytest tests/unit/test_gmail.py tests/unit/test_gmail_auth_cli.py -q
```

The browser checks include open Shadow DOM and nested iframe controls. The Gmail
checks include pagination, malformed/stale messages, acknowledgment, deadlines,
OAuth errors, and optional AI validation, without touching your mailbox.

## 3. Observe local password login

No files need editing. `configs/demo.env.example` already contains synthetic
`test-user` / `test-password` credentials accepted by the local fixture.

Open **terminal A**, set the repository directory, and start the server:

```powershell
conda run --no-capture-output -n autoweb python tests/fixtures/login_site.py --port 8765
```

Leave it running. Open `http://127.0.0.1:8765/login` in your browser to inspect the
fixture. You can also sign in manually with those synthetic credentials and click
**Perform protected action**.

In **terminal B**, set the same repository directory and run:

```powershell
conda run --no-capture-output -n autoweb python scripts/check_local_login.py
```

Expect a visible Chromium window to accept the banner, fill credentials, reach
the dashboard, and click **Perform protected action**. It should show
`Protected action completed`, print three `PASS` messages for authentication,
the protected action, and cleanup, and close after 15 seconds.

Check the two-screen variant:

```powershell
conda run --no-capture-output -n autoweb python scripts/check_local_login.py --two-step
```

The browser should fill the username, click Continue, then enter the password.
Use `--pause-seconds 30` for more observation time, or `--headless --pause-seconds 0`
for a quick run. This script targets only the local fixture profiles.

The ordinary thin runner remains available:

```powershell
conda run --no-capture-output -n autoweb python scripts/run_login.py --site configs/sites/local-password.example.json --env-file configs/demo.env.example --headed
```

It verifies login and closes immediately; it does not perform the protected action.
Stop terminal A with Ctrl+C after your checks.

## 4. Check rejected credentials

Keep terminal A running and execute:

```powershell
conda run --no-capture-output -n autoweb python scripts/check_local_login.py --invalid-password
$LASTEXITCODE
```

Expect `credentials_rejected`, exit code 1, a closed automation browser, and a
masked failure screenshot under `artifacts/login-failures/`. The script supplies
a synthetic incorrect password in memory; no credential file needs changing.
The rejection is the intended outcome, not a broken test.

If configuration references appear unresolved, remember that process environment
variables override the demo dotenv file. Remove unintended `LOCAL_LOGIN_USERNAME`
or `LOCAL_LOGIN_PASSWORD` overrides from that terminal, then rerun.

## 5. Create local Gmail configuration

The files to customize are:

| File | What to set |
| --- | --- |
| `.env` | Recipient mailbox, OAuth file paths, AI disabled, optional timeouts |
| `configs/sites/gmail-check.local.json` | Actual sender address, subject, code regex, length, and character rules |
| `secrets/gmail/credentials.json` | Downloaded Desktop OAuth client JSON, if not using an existing absolute path |
| `secrets/gmail/token.json` | Generated by authorization; do not edit its contents manually |

`.env`, `*.local.json`, `secrets/`, and runtime artifacts are ignored by Git.
Keep the tracked example profiles unchanged.

If `.env` does not exist, create it from the example. Preserve your existing `.env`
if you already have one:

```powershell
if (-not (Test-Path -LiteralPath .env)) { Copy-Item -LiteralPath .env.example -Destination .env }
if (-not (Test-Path -LiteralPath configs/sites/gmail-check.local.json)) {
    Copy-Item -LiteralPath configs/sites/email-otp.example.json -Destination configs/sites/gmail-check.local.json
}
```

Edit `.env` and supply:

```dotenv
EXAMPLE_EMAIL=your-test-mailbox@gmail.com
AUTOWEB_GMAIL_CREDENTIALS_FILE=secrets/gmail/credentials.json
AUTOWEB_GMAIL_TOKEN_FILE=secrets/gmail/token.json
AUTOWEB_AI_ENABLED=false
AUTOWEB_VERIFICATION_TIMEOUT_SECONDS=120
```

To reuse legacy files, replace the two OAuth paths with their **actual absolute
paths** using forward slashes. They can remain in the legacy repository. An
authorization operation replaces its configured token, so use a new AutoWeb token
path if you want the legacy token untouched.

For an easy first live check, send a synthetic code from a second email account.
In `configs/sites/gmail-check.local.json`, replace the `verification` object with:

```json
"verification": {
  "sender": "your-sending-account@gmail.com",
  "subject": "AutoWeb manual verification",
  "recipient": {"env": "EXAMPLE_EMAIL"},
  "code_regex": "\\b\\d{6}\\b",
  "code_length": 6,
  "code_characters": "[0-9]",
  "acknowledge": "never"
}
```

This is a fragment inside the existing profile; retain the surrounding fields and
valid JSON commas. The sender must be the actual From address, not a display name.
The profile's browser selectors are schema placeholders and are not executed by
the Gmail diagnostic. For real website mail, use that site's actual sender and a
stable subject phrase instead. Adapt length/regex/character rules to its code.

Validate the JSON/schema:

```powershell
conda run -n autoweb python -m autoweb.config --site configs/sites/gmail-check.local.json --schema-only
```

Schema-only does not check credentials or OAuth. The independent Gmail diagnostic
needs the recipient reference; it does not need website passwords.

## 6. Set up Gmail OAuth

If you already have usable credentials and a matching-scope token, skip consent
and try the diagnostic. Otherwise, in Google Cloud:

1. Select/create the project and enable the Gmail API.
2. Configure Google Auth platform branding/audience and include your mailbox as a
   test user if using an External application in testing mode.
3. Create an OAuth client of type **Desktop app** and download its JSON.
4. Save it at the configured client path. Create `secrets/gmail/` if using defaults.

See Google's [Gmail Python quickstart](https://developers.google.com/workspace/gmail/api/quickstart/python)
and [OAuth consent guide](https://developers.google.com/workspace/guides/configure-oauth-consent).
Use AutoWeb's dependency commands above rather than upgrading SDKs independently.

Run:

```powershell
conda run --no-capture-output -n autoweb python scripts/read_verification.py --authorize
```

Authorize the **recipient mailbox**, not your sending account. Expect
`Gmail authorization saved to the configured token path.` The default configured
scope is Gmail modify; this diagnostic still never marks mail read. Failed or
insufficient-scope tokens require successful consent before live retrieval works.

## 7. Verify fresh Gmail retrieval

Run:

```powershell
conda run --no-capture-output -n autoweb python scripts/read_verification.py --site configs/sites/gmail-check.local.json --show-code
```

**Wait until it prints:**

```text
Baseline captured. Request a new verification email now; waiting for fresh mail.
```

Then send this from the account configured as sender to `EXAMPLE_EMAIL`:

```text
Subject: AutoWeb manual verification
Body: Your verification code is 001234
```

Alternatively, request a new OTP manually from your test website, with the profile
configured for its mail. Request it only after the baseline message appears.
Default `conda run` captures output until completion, which is why these interactive
commands use `--no-capture-output`.

Expected output includes:

```text
Verification found; method=regex; received=...
Code: 001234
```

The leading zeros must survive. Omit `--show-code` to check the default hidden-code
behavior. The diagnostic does not acknowledge mail; messages remain unchanged by
AutoWeb. Reading them yourself in Gmail may change their read status separately.

For negative checks, restart the diagnostic each time:

- Send nothing new: expect `verification_timeout` and exit code 3. Old mail cannot win.
- Send from a different address or with another subject: expect it to remain waiting.
- Send a malformed/incorrect-length code, then a fresh valid code within the deadline:
  expect the valid message to be selected rather than stopping at the malformed one.
- Supply a nonexistent token path in your local `.env`: expect `oauth_setup_required`
  and exit code 1. Restore the correct path afterward.

You can temporarily set `AUTOWEB_VERIFICATION_TIMEOUT_SECONDS=20` in `.env` for
faster negative checks. Keep the polling interval shorter than this timeout.

## 8. Optional Gemini live check

Keep AI off for the initial checks. To exercise fallback separately, copy your
Gmail profile to another ignored `*.local.json` file. Set its `code_regex` to
`"(?!)"`, which intentionally matches nothing, and retain the correct length and
character rules. In `.env`, set:

```dotenv
AUTOWEB_AI_ENABLED=true
AUTOWEB_AI_MODEL=your-enabled-model-name
GOOGLE_API_KEY=your-local-api-key
```

Rerun the Gmail diagnostic with that fallback profile and send a new synthetic
verification message after baseline capture. Successful fallback reports
`method=gemini`. It sends decoded email text to Gemini, so use synthetic content
for this check. If deterministic regex extraction succeeds, Gemini is deliberately
not invoked. Restore AI disabled and the normal profile afterward. An unavailable
model/key or invalid AI result can lead to a timeout; AI fallback failures do not
replace deterministic Gmail behavior.

## 9. Real website password profiles

This is optional; the local fixture already verifies the implemented behavior.
Copy `configs/sites/password.example.json` to an ignored `*.local.json` profile.
Change `entry_url`, credential environment references, ordered steps/locators,
success checks, and failure checks to match your test website. Supply those referenced
credentials only in `.env`. Use an authenticated UI element for success; add URL
or same-origin session/API assertions where appropriate.

Validate the profile, then run it with `scripts/run_login.py --site ... --headed`.
The example.com examples are schema examples, not ready-made real-site integrations.
Sites requiring email OTP cannot yet complete through this runner.

## Troubleshooting

| Symptom | Check |
| --- | --- |
| `ModuleNotFoundError: autoweb` | Install the editable package in conda autoweb |
| Chromium executable missing | Run the matching Playwright Chromium install command |
| Demo connection refused | Keep the fixture server running on port 8765 |
| Port 8765 already occupied | Stop the other server, or change both profiles' entry URLs to match another demo port |
| Optional demo banner skipped | This is allowed when the banner is absent |
| `oauth_client_file_missing` | Check `.env` client path and downloaded Desktop client JSON |
| `token_invalid`, `token_refresh_failed`, `oauth_scopes_insufficient` | Check the token path; authorize again if needed |
| `mailbox_access_denied` | Check Gmail API enablement, mailbox authorization, and scopes |
| `verification_timeout` | Check exact sender/recipient, subject, code rules, fresh timing, and timeout |
| `unsupported_login_mode` | OTP browser orchestration is Phase V and remains pending |

The deterministic suite verifies acknowledgment and API failure handling without
modifying real messages. This walkthrough performs no automatic website OTP flow.
